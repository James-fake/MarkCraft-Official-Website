## 1. 项目概览

### 1.1 项目目标

为 MarkCraft 建立一个具有鲜明品牌气质的产品官网。网站不应只是功能清单或常见 SaaS 模板，而应通过一段具有节奏的浏览体验，让访客理解：MarkCraft 不只是 Markdown 编辑器，更是把记录、连接、整理、创作串联起来的个人知识工作空间。

网站需要完成三件事：

1. **建立理解：** 用清晰的叙事说明 MarkCraft 解决什么问题、如何工作、与普通 Markdown 编辑器有什么不同。
2. **提供体验：** 让访客在浏览器中体验一段安全、轻量、可控的演示流程，而不是被迫阅读所有功能说明。
3. **推动下载：** 在用户理解产品后，给出清晰的 Windows 下载入口，并公开必要的版本、系统要求、安装与数据说明。

### 1.2 产品概况

- **产品名称：** MarkCraft
- **定位：** 现代化 Markdown 编辑器、个人知识工坊、博客生成器
- **技术背景：** React 18、TypeScript、Vite；桌面端采用 Electron
- **编辑引擎：** CodeMirror 6 源码编辑模式与 Tiptap 3 所见即所得模式，可无缝切换
- **核心理念：** 让笔记从“孤岛”连接成“网络”，让知识库成为个人的“第二大脑”
- **数据架构概况：** 小型状态数据使用 localStorage；笔记树、知识库、白板、版本等内容写入磁盘文件。官网不得把这一概括夸大成未经验证的安全保证。
- **当前支持平台：** Windows（具体最低版本、架构与安装包规格待核实）

### 1.3 已知功能范围

以下为项目目前提供的功能描述。官网上线前，应由产品负责人逐项确认当前发行版本是否均已实现、稳定且可供用户使用。

- 双引擎 Markdown 编辑：源码模式与所见即所得模式
- Excalidraw 混合引擎白板（Canvas v2）
- 双向链接、反向链接、块引用与嵌入
- 3D 知识图谱，支持力导向、同心圆、树形、网格等布局
- 可检索、可问答的 AI 知识库
- 嵌套标签
- Markdown 导出 PDF、DOCX、EPUB 等多种格式（项目资料提及共 12 种，最终列表待核实）
- 博客工坊，包含 64 种主题（需确认数量与可用状态）
- 47 条命令面板操作（需确认统计口径）
- 三套可配置快捷键绑定
- 多套编辑器与代码主题（资料提及 6+6 套，需确认具体含义）

### 1.4 最大差异化

MarkCraft 的核心价值不是“支持 Markdown”，而是将以下工作流连成一体：

**捕捉想法 → 编辑内容 → 连接相关笔记 → 发现知识结构 → 复用知识 → 输出文章或其他格式。**

博客工坊和一键部署是潜在的强卖点，但博客一键部署当前状态尚未确定。若尚未正式上线，只能作为开发中能力或未来方向，不能在首页用已上线功能的口吻宣传。

### 1.5 设计方向

- 高级、精致、具有艺术指导感与杂志美学
- 长篇沉浸式滚动叙事，章节之间形成有节奏的视觉变化
- 浅色与深色场景交替，但整体视觉语言统一
- 首屏以品牌文字、留白和排版建立气质，不用产品截图或知识图谱作为唯一主角
- 视觉高潮均衡分布，不把所有效果堆在一个区块
- 避免常见 SaaS 模板感、过度企业化、赛博科技感、过度 AI 化和泛滥的渐变光效
- 先制作精致、可交互的演示体验；不在官网内复刻完整桌面应用

### 1.6 成功标准

- 新访客在首屏能理解 MarkCraft 大致是什么，并看到“体验 Demo”和“下载应用”两个入口。
- 浏览完首页后，用户能复述“编辑—连接—整理—创作”的核心工作流。
- Demo 有清晰的开始、探索和结束路径；每个可点击元素都有可见反馈。
- 真实产品截图与官网演示的界限清楚，不以虚构界面冒充产品实况。
- 下载链接、版本、系统要求、数据处理说明真实且可验证。
- 桌面、平板、手机布局可用，支持键盘操作和减少动态效果偏好。

## 2. 产品定位与信息原则

### 2.1 主要受众

1. **Markdown 使用者：** 希望有流畅编辑体验，同时保留 Markdown 工作方式的人。
2. **知识管理用户：** 使用双向链接、标签、反链和图谱管理个人知识的人。
3. **写作者与创作者：** 希望把零散笔记发展成文章、博客或可分享内容的人。
4. **重视数据掌控的个人用户：** 希望理解自己的资料如何保存、由自己如何管理的人。

网站不要假设所有访客都熟悉知识图谱、双向链接或编辑器引擎名称。首次出现时，应先用用户收益解释，再补充技术名称。

### 2.2 核心信息层级

- **第一层：** 让想法彼此连接，并最终成为作品。
- **第二层：** 一个工作空间里完成 Markdown 编辑、知识连接、视觉整理与内容输出。
- **第三层：** 双编辑引擎、反链、图谱、白板、AI 知识库、主题和多格式导出等具体功能。
- **第四层：** 技术栈、支持平台、版本、存储方式、系统要求和隐私说明。

### 2.3 信息表达原则

- 从用户场景开始，不从技术名词开始。
- 每一屏只传达一个主要观点。
- 功能介绍必须回答“这对用户有什么用”。
- 不能把“开发中”“计划中”写成“现在就能使用”。
- 不能承诺“绝对安全”“数据永不上传”“完全离线”等未经验证的隐私或网络行为。
- 如果 AI 功能需要外部服务，应说明数据发送范围、服务提供方与相关设置；未核实前不得写确定性承诺。
- 不使用虚构用户评价、下载量、媒体背书或未经证实的性能数字。

## 3. 品牌概念与视觉系统

### 3.1 品牌概念方向

**暂定创意主题：** `A Studio for Thought.`  
**中文释义：** 一个让思想成形的地方。

**核心文案草案：** `Your thoughts, connected.`  
**中文辅助表达：** 从一篇笔记，到一个知识网络，再到属于你的作品。

这些是设计提案，不是最终锁定的品牌规范。进入视觉设计阶段后，可通过真实产品界面和标识草图进一步验证。

### 3.2 标识概念

目前没有既有 Logo 或完整品牌系统，建议从产品理念中提炼符号，而不是使用常见的 AI 星芒、机器人、芯片或发光脑部图形。

可探索的概念：

- **连接中的字形：** 从 M、C 或书写笔画中提炼出“两个点通过一条路径连接”的抽象结构。
- **编辑标记：** 将光标、括号、引用线或折页结构简化成独立符号。
- **知识路径：** 使用少量节点与线段构成克制的连接关系，既可用于 Logo，也可用于页面章节过渡。

标识需要在 16–24 px 小尺寸下仍可识别；不依赖复杂渐变、阴影或细碎线条。最终方案应提供深色背景、浅色背景、单色和小尺寸版本。

### 3.3 色彩系统（初始提案）

| 角色   | 名称         | 色值        | 使用建议                |
| ---- | ---------- | --------- | ------------------- |
| 主背景  | Paper      | `#F3F0E8` | 暖纸白，用于主要叙事区域        |
| 主文字  | Ink        | `#242521` | 深墨色，用于标题、正文与主要图形    |
| 辅助色  | Growth     | `#D9E2D3` | 柔和灰绿，用于连接、选中状态与局部强调 |
| 深色背景 | Night      | `#20221F` | 用于图谱、编辑器或深色章节       |
| 次级文字 | Muted Ink  | `#73756D` | 用于注释、说明和元信息，需验证对比度  |
| 分隔线  | Quiet Line | `#D7D4CC` | 轻量边界，避免粗重卡片框线       |

以上颜色仅为起点。最终色板需在真实显示器、浅色与深色场景、按钮状态、焦点状态和 WCAG 对比度测试中校准。避免用颜色作为唯一的信息区分手段。

### 3.4 字体与排版

- 英文标题：选择具有编辑感的现代衬线体或精致 Grotesk 字体，体现出版物气质。
- 中文标题：选择笔画清晰、字面舒展的现代黑体；避免过度科技感字体。
- 正文：优先可读性与跨平台稳定性；提供系统字体回退栈。
- 代码和界面数据：使用清晰的等宽字体。
- 不要依赖必须联网才能加载的字体；若使用远程字体，应配置合理回退与加载失败方案。

排版建议：

- 首屏主标题采用大字号与宽松行距，控制行宽，避免长句横跨整个屏幕。
- 中英文标题之间保持明确层级，不把所有文字都做成大标题。
- 用留白、对齐和字体变化建立节奏，不靠大量卡片、边框和阴影堆层次。
- 正文行长控制在适合阅读的范围内；移动端避免过小字号。

### 3.5 图形语言

- 以节点、连线、括号、引用线、光标、页边距和纸张分栏作为主要视觉语汇。
- 节点关系应有层级与疏密，不做随机无意义的“科技粒子背景”。
- 允许出现纸张纹理、轻微颗粒或印刷感，但强度必须低，不能影响阅读和性能。
- 动态线条应表达“连接”“引用”“组织”等真实产品概念，不只是装饰。
- 图形优先使用 SVG、CSS 或 Canvas 绘制；不要把整屏做成大体积视频背景。

### 3.6 图片与产品界面规则

- 真实产品界面只能来自当前可运行版本的实际截图或录屏。
- 不使用 AI 生成的假界面冒充真实软件。
- 为官网演示制作的虚构内容必须标注为演示数据。
- 产品截图应统一窗口比例、缩放、主题和示例内容，避免素材之间风格割裂。
- 截图应突出功能重点，必要时可裁切，但不能通过后期改造让不存在的功能看起来已上线。

### 3.7 品牌语气

- 清晰、克制、有想象力，但不故作玄虚。
- 以创作者和知识工作者的语言描述收益。
- 可以使用“思想”“连接”“工作坊”“作品”等意象，但必须由具体功能承接。
- 避免“革命性”“颠覆行业”“全网第一”“无限可能”等无证据的夸大词。

## 4. 网站信息架构

### 4.1 第一阶段页面结构

第一阶段建议先建设一个长篇沉浸式首页，避免在内容尚未稳定时拆成大量页面。

- `/` — 官网首页：产品叙事、功能展示、Demo 入口、下载入口、信任信息
- `/demo` 或首页内嵌 Demo 区域 — 浏览器内交互演示（推荐优先采用首页内嵌或独立锚点，减少跳转）
- `/privacy` — 隐私说明（若尚无独立页面，至少在首页提供明确入口与简版说明）
- `/release-notes` — 版本记录（可在有稳定发布节奏后上线）

如当前只做最小版本，可先完成首页、Demo 和隐私说明入口；不要为了显得完整而添加空白页面。

### 4.2 导航结构

桌面导航建议：

- 左侧：MarkCraft 品牌标识
- 中间：`Product`、`Experience`、`Philosophy` 或对应中文锚点
- 右侧：`体验 Demo`（次级入口）、`下载应用`（主入口）

导航应简洁，不设置十几个功能下拉菜单。页面滚动后可以缩小高度或改变背景，但不能突然抢占注意力。

### 4.3 页面叙事顺序

1. **The Thought** — 思想从这里开始：品牌与核心价值
2. **The Craft** — 让表达顺畅发生：双引擎编辑与创作体验
3. **The Connection** — 让笔记不再孤立：双向链接、反链与知识图谱
4. **The Possibility** — 让知识产生更多可能：白板、AI 知识库、博客工坊与导出
5. **Make It Yours** — 把它变成你的工作方式：下载、平台与信任信息
6. **Footer** — 版本、隐私、联系渠道和必要链接

## 5. 首页逐屏设计规范

### 5.1 屏幕 01 — Hero / The Thought

**目标：** 建立第一印象，说明产品不是单纯的 Markdown 文本框，并立即提供两个清晰入口。

**布局：**

- 暖纸白背景，大量留白。
- 左侧或居中偏左采用品牌排版，避免常见居中 SaaS Hero 的模板感。
- 以 MarkCraft 名称、主标题、简短说明和两个 CTA 为主体。
- 右侧或下方可放置极简的抽象连接符号，或者逐渐展开的纸张/文字路径；不要让产品截图或知识图谱独占首屏。
- 首屏底部设置轻量的向下探索提示。

**文案草案：**

> **A Studio for Thought.**  
> 让想法有地方生长。
>
> 从一篇 Markdown 笔记开始，连接你的知识，最后把它变成作品。

CTA：

- 主按钮：`体验 Demo`
- 次按钮：`下载 MarkCraft`

**交互：**

- 页面进入时标题与图形以短距离、低幅度动效出现；不使用夸张弹跳或长时间等待。
- 主按钮点击后滚动至 Demo 或进入 Demo 页面。
- 下载按钮跳转到下载区或真实下载地址；在真实地址尚未配置时，开发环境可显示明确的占位提示，但生产环境不能把占位地址作为可用下载。

**验收：**

- 首屏在常见桌面分辨率下不显拥挤。
- 两个入口无需滚动即可找到。
- 无自动播放声音、无强制等待动画。

### 5.2 屏幕 02 — Product Statement / 从工具到工作流

**目标：** 用一段短叙事解释 MarkCraft 的独特价值。

**布局：**

- 从单张笔记卡片逐步出现相关节点，再转化成一篇文章的结构。
- 动画仅用于解释过程，最终停留在清晰静态画面。
- 可使用横向分栏或纵向滚动的三阶段叙事：记录、连接、创作。

**核心表达：**

> 笔记不必停留在被保存的那一刻。  
> 它们可以彼此连接，也可以成为下一篇作品的起点。

**验收：**

- 用户能理解从笔记到知识网络再到作品的流程。
- 动画关闭后，内容仍完整可读。

### 5.3 屏幕 03 — The Craft / 双引擎编辑

**目标：** 展示编辑体验的灵活性，说明源码模式与所见即所得模式并不是两个割裂的产品。

**视觉方案：**

- 以一段真实 Markdown 内容为中心。
- 通过切换或滑动对比展示源码视图与富文本视图。
- 使用实际产品截图或经过确认的产品录屏；如果用网站内绘制的模拟界面，必须明确它是示意图。
- 辅助说明快捷键、命令面板和主题定制，不把所有设置一次性铺满。

**内容重点：**

- CodeMirror 6：适合偏好直接编辑 Markdown 源码的用户。
- Tiptap 3：适合更直观地编辑与组织内容的用户。
- 根据实际产品行为，说明两种模式如何切换以及格式兼容边界。

**文案草案：**

> **Write the way you think.**  
> 有时需要掌控每一个字符，有时只想专注表达。MarkCraft 让两种编辑方式在同一套工作流中自然切换。

**交互：**

- 点击 `源码模式` / `所见即所得` 切换演示画面。
- 切换后标题、代码片段或预览区域同步变化。
- 该切换只用于展示，不应暗示网站具备完整桌面编辑器能力。

### 5.4 屏幕 04 — The Connection / 知识连接

**目标：** 将双向链接、反链、块引用和知识图谱转化为容易理解的体验。

**视觉节奏：**

1. 先展示一篇笔记。
2. 出现与它相关的笔记链接。
3. 展示反向链接，让用户看到“哪些内容正在引用这篇笔记”。
4. 画面从局部连接逐渐过渡到整体知识图谱。
5. 最后切换到真实产品界面，证明抽象视觉与实际功能对应。

**设计注意：**

- 图谱不应出现过多节点，避免变成视觉噪声。
- 重点节点应有标签或说明，关系线要表达层级。
- 图谱运动速度缓慢、可暂停，并尊重减少动态效果设置。
- 知识图谱中的节点内容使用电影与创作主题的演示数据。

**文案草案：**

> **A note is never alone.**  
> 通过双向链接、反向链接与知识图谱，重新发现那些原本分散在不同笔记里的关系。

### 5.5 屏幕 05 — The Possibility / 从知识到作品

**目标：** 让用户看到知识不仅可以被保存，还能被整理、绘制、检索和输出。

建议分成四个内容点，但视觉上不要做成四张完全相同的功能卡片：

1. **Canvas / 白板：** 用视觉方式整理想法和关系。
2. **AI Knowledge Base / AI 知识库：** 在已有知识中检索并进行问答；必须根据真实数据处理方式说明限制。
3. **Blog Studio / 博客工坊：** 将笔记整理为可阅读的文章，并预览不同主题。
4. **Export / 多格式导出：** 根据真实支持列表展示导出格式。

**表现方式：**

- 一段内容从笔记文本转换为白板节点，再成为文章预览。
- 使用轻量过渡连接模块，不要让四个功能像互不相关的插件。
- 若展示“发布”或“一键部署”，必须先核实功能已正式可用；否则只展示文章预览与导出流程，并标注部署能力为开发中或不展示。

**文案草案：**

> **Knowledge wants to move.**  
> 让一条笔记成为一个想法、一张图、一篇文章，或下一次创作的起点。

### 5.6 屏幕 06 — Browser Demo / 亲自探索

**目标：** 让用户用一段短体验验证产品理念，而不是只看营销动画。

**布局：**

- 在页面内嵌入交互式演示工作区，或跳转到独立 Demo 页面。
- 左侧显示推荐步骤，中央显示演示内容，右侧或底部显示当前步骤说明。
- 提供“按推荐路线体验”和“自由探索”两种入口。
- 明确提示这是网站演示数据，不会访问访客的本地笔记。

**演示路线：**

1. 记录一条电影观察。
2. 点击一个双向链接，查看相关笔记。
3. 在知识图谱中选择节点，探索它的关系。
4. 打开预设 AI 问答，查看演示知识库如何被检索与复用。
5. 将笔记整理成文章，并预览博客工坊主题。

**验收：**

- 用户可跳过步骤或重新开始。
- 每个可交互元素均有反馈。
- 任何看似输入框的元素都必须说明输入是否会被处理；若只是预设演示，不应伪装成真实 AI 请求。
- 不要求登录、不访问用户本地文件、不调用真实 AI 服务、不真正发布博客、不写入用户真实数据。

### 5.7 屏幕 07 — Make It Yours / 下载与信任

**目标：** 在用户理解产品后，提供下载决策所需的信息。

**内容顺序：**

1. 产品价值总结。
2. 明确的 Windows 下载按钮。
3. 版本号、发布日期、安装包大小、系统要求、CPU 架构和数字签名信息（仅在确认后展示）。
4. 简短数据存储说明，并链接到完整隐私说明。
5. 安装或常见问题入口（若已有相应资料）。

**文案草案：**

> **Make room for your thoughts.**  
> 从下一条笔记开始，慢慢建立属于你的知识工作流。

CTA：`下载 Windows 版`

**重要：** 下载链接与版本数据当前未在本蓝图中提供。开发时应从集中配置读取，不得硬编码虚构地址、版本号或安装包大小。

### 5.8 Footer / 页脚

建议包含：

- MarkCraft 标识与一句品牌说明
- 产品 / Demo / 下载锚点
- 隐私说明
- 版本记录（如已上线）
- 联系方式或反馈渠道（需由产品方提供真实地址）
- 版权年份

不要展示无效的社交媒体图标、空白链接或虚构联系邮箱。

## 6. 浏览器内 Demo 体验规范

### 6.1 Demo 定位

Demo 是一段有引导的交互演示，不是网页版 MarkCraft，也不是完整桌面软件的替代品。它的目标是让用户理解知识如何从单条笔记发展成关系网络和创作成果。

### 6.2 演示主题与数据

统一使用“电影与创作”作为虚构示例知识库主题。内容应原创、简洁，避免复制受版权保护的长篇评论或书籍内容。

建议演示笔记：

- `电影中的静止镜头`
- `空间如何塑造人物`
- `侯孝贤与日常时间`
- `长镜头与观众注意力`
- `从观察到影评`

建议标签：`电影语言`、`镜头`、`创作笔记`。

演示文章标题：`静止的画面，流动的时间`。

这些是 Demo 的虚构示例内容，不代表 MarkCraft 自带该主题知识库。

### 6.3 推荐路线

**步骤 1：捕捉观察**

- 显示一条简短笔记。
- 提供一个明确的“查看相关笔记”操作。
- 说明：每篇作品都可以从一个观察开始。

**步骤 2：发现关联**

- 点击“空间如何塑造人物”等关联笔记。
- 显示双向链接或相关笔记面板。
- 高亮两篇笔记之间的关系，并说明关系来自演示数据。

**步骤 3：看见整体**

- 打开简化知识图谱。
- 用户可以选择节点，查看标题、标签和一条关系说明。
- 提供列表视图作为图谱的替代方式，保证移动端与键盘可用性。

**步骤 4：复用知识**

- 展示一个预设问答，例如：“这些笔记里，哪些内容都在讨论时间感？”
- 返回预设答案与相关笔记引用。
- 明确标注“预设演示结果”，不要伪装成实时 AI 推理。

**步骤 5：组织成作品**

- 把几条笔记组织为文章大纲。
- 展示博客主题预览。
- 最终提供“重新体验”或“了解桌面版”入口。

### 6.4 自由探索模式

自由探索至少支持：

- 选择笔记
- 打开相关笔记
- 在图谱与列表视图之间切换
- 查看预设问答
- 预览文章
- 重置演示

不需要实现完整 Markdown 编辑器、完整白板、真实 AI 推理、真实导出、真实文件读写或博客发布。

### 6.5 状态与交互反馈

- 当前步骤必须清晰可见。
- 已完成步骤可以显示完成状态，但不要只靠颜色区分。
- 所有按钮必须有正常、悬停、聚焦、按下、禁用状态。
- 不存在的功能不可使用“即将打开”之类模糊反馈；应明确告诉用户当前 Demo 的边界。
- 重置演示时可立即恢复初始状态，不需要重新加载整个网站。

### 6.6 Demo 数据结构建议

```ts
type DemoNote = {
  id: string;
  title: string;
  excerpt: string;
  tags: string[];
  linkedNoteIds: string[];
  backlinks?: string[];
};

type DemoQuestion = {
  id: string;
  question: string;
  answer: string;
  sourceNoteIds: string[];
  isPreset: true;
};
```


数据建议集中放在独立文件中，例如 `src/data/demoNotes.ts`、`src/data/demoQuestions.ts`。不要将所有示例数据散落在多个 UI 组件中。

### 6.7 Demo 安全边界

- 不读取访客本地文件或桌面应用数据。
- 不要求登录。
- 不调用真实 AI API。
- 不将访客输入发送到服务器；如确需输入交互，应明确其仅在浏览器内处理，且不持久化。
- 不真正发布博客或上传内容。
- 不在演示中使用真实用户数据。
- 不以模拟结果冒充真实服务状态。

## 9. 交互、动效与无障碍

### 9.1 动效原则

动效必须服务于理解和节奏，而不是证明网站“有动画”。

- 优先使用淡入、位移、遮罩揭示、线条生长与轻量视差。
- 单次动效通常控制在短时间内；避免连续等待用户才能阅读内容。
- 滚动驱动的动效必须有静态回退方案。
- 避免大范围持续漂浮、强烈闪烁、快速缩放和无意义的粒子效果。
- 不让关键文案在动画结束前不可读。
- 重要内容不应只在鼠标悬停时出现。

### 9.2 滚动叙事

- 章节进入时可改变背景色或图形状态，但不应让用户迷失页面位置。
- 可设置轻量章节进度提示，但不要用过度抢眼的滚动进度条。
- 不应使用强制滚动锁定，让用户无法按自己的速度浏览。
- 移动端减少复杂的固定定位与大面积视差。

### 9.3 响应式布局

**桌面端：** 完整长篇叙事、并排内容、较复杂图谱和 Demo 工作区。  
**平板端：** 减少并排列数，控制图谱尺寸，优先保留主要操作。  
**手机端：** 单列布局；导航收敛；图谱提供列表替代；演示步骤变成易操作的纵向流程；CTA 保持易触达但不遮挡内容。

建议至少测试：

- 360 px 宽手机
- 390–430 px 宽手机
- 768 px 平板
- 1024 px 小型桌面
- 1280 px 常见桌面
- 1440 px 及以上宽屏

### 9.4 键盘与无障碍

- 所有按钮、链接、切换器与 Demo 控件可通过键盘访问。
- 焦点样式清晰可见，不得为了视觉整洁而移除焦点轮廓。
- 图谱中的节点应提供可访问名称；无法用键盘操作的图形需提供列表视图。
- 图片提供有意义的替代文本；纯装饰图片使用空替代文本。
- 颜色对比度需验证，不能只用颜色传达状态。
- 支持 `prefers-reduced-motion`，减少动态效果时仍保留完整内容和交互。
- 为页面设置正确的标题层级、语言属性、链接名称和语义化区域。

### 9.5 性能

- 优先加载首屏必需资源，其余截图延迟加载。
- 对真实截图进行尺寸裁剪和压缩，避免传输超大原图。
- 避免引入只用于一个微小效果的大型动画依赖。
- 不在页面启动时一次性初始化复杂图谱；进入相关章节或 Demo 时再加载。
- 在低性能设备上确保滚动与按钮响应不受持续动画影响。

## 10. 技术实施建议

```ts
  version: "", // 发布前填写已核实版本
  releaseDate: "",
};
```

生产环境中，如果下载地址或版本信息为空，应显示明确的“下载信息正在准备”状态或阻止构建发布，而不是生成看似真实的假信息。

### 10.4 组件拆分原则

- 每个主要章节使用独立组件。
- Demo 状态、演示数据和视觉组件分离。
- 不把整站写进一个巨型组件。
- 不重复实现按钮、导航、容器、章节标题等基础组件。
- 动效封装为可复用的小组件，并提供无动效回退。
- 内容与布局尽量分离，方便修改文案和功能状态。

### 10.5 状态管理

第一版 Demo 可使用 React 本地状态或 `useReducer`。状态应清晰覆盖：

- 当前演示步骤
- 当前选中的笔记
- 当前视图（图谱 / 列表）
- 当前打开的预设问答
- 当前文章预览状态

不要为了一个纯前端演示引入复杂的全局状态系统，除非现有项目已经使用并且确有必要。

### 10.6 SEO 与分享

- 为首页设置唯一、准确的标题与描述。
- 配置 favicon 与 Open Graph 分享图。
- 使用语义化标题结构。
- 不把关键文案只绘制在图片里。
- 不添加虚构评分、结构化数据或产品评论。
- 如果使用分析工具或第三方脚本，应在隐私说明中如实披露。

### 10.7 安全边界

- 官网 Demo 不应接触 Electron 主进程或桌面文件系统。
- 不把 API 密钥写入前端代码。
- 不在未确认的情况下将访客输入发送到外部服务。
- 外部链接应使用明确的目标与安全属性。
- 下载链接应指向可信的官方发布地址，并在上线前验证文件完整性和签名信息（如有）。

## 11. 下载、隐私与信任信息

### 11.1 下载区必须提供的信息

上线前核实并填写：

- 当前稳定版本号
- 发布日期
- Windows 最低系统要求
- 支持的 CPU 架构（如 x64、ARM64；以实际构建为准）
- 安装包格式与大小
- 官方下载直链
- 安装或升级注意事项
- 数字签名或校验和信息（若已提供）
- 已知问题与反馈渠道

如果其中部分信息暂时没有，不应猜测或编造。可先展示已确认的信息，并将未确认项暂不公开。

### 11.2 数据存储说明

现有产品资料指出：小型状态数据使用 localStorage；笔记树、知识库、白板与版本等内容存储于磁盘文件。官网应把这一点写成通俗、准确的说明，并由开发者核实具体实现细节。

建议说明结构：

1. 哪些数据保存在本地浏览器或应用存储中。
2. 哪些笔记、白板、版本数据保存在用户设备磁盘。
3. AI 知识库是否会向外部模型或服务发送内容；如果会，发送哪些数据、由谁处理、如何关闭或配置。
4. 遥测、崩溃报告、更新检查或第三方资源是否存在。
5. 用户如何备份、迁移和删除数据。

在以上内容核实之前，不要直接写“所有数据始终只存在本地”或“任何数据都不会上传”。

### 11.3 信任设计

- 使用简短、可理解的说明，不使用大面积盾牌图标或夸张的安全徽章。
- 让用户知道数据由什么机制保存，而不是只写“我们重视隐私”。
- 如果尚未发布正式隐私政策，应在上线前完成；不能用一句宣传口号替代完整说明。
- 不使用虚构的认证标志、开源标志或第三方背书。

## 12. 开发阶段与交付顺序

### 阶段 0：项目核查

- 检查是否已有官网代码、构建脚本和部署环境。
- 确认真实产品截图、Logo、下载包和发布信息的位置。
- 确认所有功能的上线状态。
- 输出缺失素材与风险清单。

**交付：** 项目现状说明、素材缺口清单、实施计划。

### 阶段 1：设计系统与静态首页

- 建立色彩、排版、间距、容器、按钮和章节系统。
- 完成导航、Hero、工作流、编辑器、连接、可能性、下载和页脚的静态结构。
- 接入真实产品素材；缺少素材时使用明确的占位框，不伪造真实界面。
- 完成桌面与移动端基础布局。

**交付：** 可浏览的静态首页。

### 阶段 2：滚动叙事与轻量动效

- 加入章节进入、线条连接、界面切换等动效。
- 为减少动态效果偏好提供回退。
- 测试低性能设备上的滚动表现。

**交付：** 动效完善的首页。

### 阶段 3：浏览器内 Demo

- 建立独立演示数据与状态管理。
- 实现推荐路线与自由探索。
- 实现笔记切换、链接关系、图谱/列表切换、预设问答与文章预览。
- 明确标注演示边界。

**交付：** 可重复体验的交互 Demo。

### 阶段 4：下载、隐私与上线检查

- 接入真实下载链接与发布信息。
- 完成隐私说明、SEO、分享图和 favicon。
- 进行键盘、无障碍、响应式、性能与链接检查。
- 运行生产构建并验证部署结果。

**交付：** 可发布官网与上线验收记录。

### 防返工原则

- 先核查项目，不直接推倒重写。
- 先完成结构与视觉基线，再逐章加入动效。
- 先让静态内容完整，再实现 Demo 状态。
- 每阶段先验收，再进入下一阶段。
- 不为新增章节重写已验收的组件。
- 不改变现有项目结构，除非核查后有明确理由并获得确认。
- 不用假数据或假链接掩盖缺失的真实资源。

## 14. 待确认事项

下列事项必须在正式上线前由产品负责人或开发者确认：

1. **下载信息：** 官方直链、版本号、发布日期、安装包大小、支持架构、最低 Windows 版本。
2. **功能上线状态：** AI 知识库、博客工坊、白板、图谱、导出格式数量、命令数量与快捷键方案的当前可用情况。
3. **博客发布能力：** 是否已有真实的一键部署能力；若未完成，应仅展示预览流程或标记为开发中。
4. **数据与隐私：** AI 调用链路、外部服务、遥测、更新检查、崩溃报告、备份与删除机制。
5. **品牌资产：** 最终 Logo、字体授权、正式色板与分享图。
6. **联系渠道：** 反馈邮箱、问题追踪地址或其他真实联系方式。
7. **部署方式：** 网站托管平台、域名、HTTPS 与发布流程。
8. **素材版本：** A01–A10 截图是否来自同一稳定版本。

在这些事项完成核查之前，可以进行视觉设计和静态页面开发，但不要把未经确认的信息写入正式下载区、隐私承诺或功能承诺。

## 最终设计原则摘要

MarkCraft 官网应当像一次有节奏的知识探索：从一个想法开始，让访客看见笔记如何被编辑、连接、重新理解，最后变成一篇作品。视觉上要克制而有记忆点；交互上要轻巧、清楚、有反馈；产品表达必须准确，真实界面必须可验证；下载与隐私信息必须诚实。

**最终目标不是让网站看起来“很 AI”，而是让用户感受到：MarkCraft 能帮助自己更自然地思考、组织知识并完成创作。**
